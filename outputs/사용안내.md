[간결한 화면 사용 안내](화면_사용안내.md): 상세 설정·범위·그룹 설정·통신 기록은 필요할 때 펼칩니다.

실행과 연결 방법은 [모델별 연결 안내](모델별_연결안내.md)를 먼저 확인하세요. 기존 기능을 유지하면서 RS232(USB 컨버터 포함), 모델별 USB·LAN·GPIB, 구형 모델 턴코일 LCOMP 처리를 추가했습니다.

# Fluke 5560A 통신·순차 실행 개선판 v5.4.0

v5.4.0에는 전류·전력 행을 작은 전류와 큰 전류 그룹으로 나누어 실행하는 옵션을 추가했습니다. 사용법과 3 A 작업 기준 / 3.1 A 단자 기준의 차이는 같은 폴더의 `전류그룹_사용안내.md`를 참고하세요. 이전 통신 개선도 포함합니다.

## 턴코일과 LCOMP 적용 조건

공식 매뉴얼 Rev. 3 기준으로 LComp는 외부 **52120A 증폭기가 연결되고 활성화된 단일 AC 전류(ACI) 출력**에서 제공됩니다. 5560A에 턴코일만 직접 연결하는 구성의 일반 `LCOMP ON` 명령은 명령 목록에 없습니다. 공식 원격 명령은 `LCOMP_52120 ON/OFF` 및 상태 조회 `LCOMP_52120?`이며 52120A의 AC 출력 보상용입니다. 전력 출력이나 DC 전류에 동일하게 적용하는 기능으로 안내되어 있지 않습니다. [사용 설명서 본문 45쪽](https://media.fluke.com/98e20aac-6ee7-4151-8b35-b2fb011adb6b_original%20file.pdf), [프로그래밍 매뉴얼 본문 81쪽](https://media.fluke.com/b2b30a71-26d0-4067-be01-b308017892a8_original%20file.pdf)

현재 프로그램의 턴코일 옵션은 실제 출력 전류를 턴수로 환산하는 기능입니다. LCOMP 활성화와는 별개입니다. 사용자가 외부 52120A 없이 턴코일만 사용한다고 확인했으므로 v5.4.0에는 LCOMP 자동 명령을 추가하지 않았습니다. `COILTYPE`로 본체의 코일 표시를 선택하는 기능도 LCOMP를 켜는 기능과는 다릅니다.


## 이번 수정: 측정 도중 시간 초과로 연결이 끊기는 현상

제공된 사진의 오류는 `*OPC?` 완료 응답 대기 중 발생했습니다. 기존 코드는 일반 조회 제한 시간(기본 3초)을 출력 안정화 대기에도 사용하고, 시간이 초과되면 TCP 연결을 직접 닫았습니다. 특정 행뿐 아니라 전류 등 다른 항목에서도 발생한다는 설명과 함께 볼 때 이 처리가 가장 유력한 원인입니다. 사진만으로 실제 LAN 단선·장비 내부 오류를 배제할 수는 없습니다.

사진의 `OUT -100 V, 0 HZ; OPER`는 16행 성공 기록입니다. 실패한 17행의 실제 명령은 기존 로그에 남지 않아 그 값으로 원인을 단정하지 않았습니다.

공식 프로그래밍 매뉴얼 본문 39쪽에 따르면 `*OPC?`는 이전 OUT 명령의 출력이 안정된 뒤 `1`을 응답합니다. 단순한 연결 확인 응답이 아닙니다.

v5.3.2 변경 사항:

- 일반 조회 3초와 **출력 완료 대기 60초**를 분리했습니다. 60초는 이 프로그램의 기본값이며 장비의 보장 응답 시간이 아닙니다. 화면에서 1~300초로 조정할 수 있고, 정상 응답이 먼저 오면 즉시 다음 절차로 진행합니다.
- 한 번 보낸 출력 명령과 `*OPC?`를 자동 재전송하지 않습니다. 늦게 온 응답도 같은 작업의 응답으로 받도록 기다립니다.
- 출력·순차 실행·수동 조회를 별도 작업으로 처리하므로 완료 응답을 기다리는 동안 화면이 멈추지 않습니다. 다음 행의 유지시간은 완료 확인 뒤 시작합니다.
- 대기 중 **STBY**를 누르면 다음 행을 중단하고 현재 응답 대기를 취소하여 STBY 전송을 시도합니다. LAN은 짧은 간격으로 취소를 확인합니다. USB/GPIB는 드라이버 읽기가 반환할 때까지 취소가 지연될 수 있습니다.
- 최종 시간 초과·통신 종료 시 STBY를 시도한 다음 연결을 정리합니다. 늦은 응답을 새 명령의 결과로 오인하지 않도록 자동 재접속·자동 출력 재개는 하지 않습니다. **STBY 전송 시도만으로 출력 차단 성공을 표시하지 않습니다.** 상태가 미확인이면 장비 본체에서 확인하세요.
- 장비가 ERR?에 실제 오류를 반환했을 때는 오류 코드를 기록하고 STBY 및 OPER?=0을 확인합니다. 확인에 성공하면 연결을 유지하면서 순차 실행을 중단합니다. 오류는 숨기거나 자동으로 건너뛰지 않습니다.
- 실행 전 행 번호와 실제 명령, 응답, 소요 시간, 실패 원인을 기록합니다. 프로그램 폴더의 `logs`에 날짜별 실행 파일을 자동 저장합니다. 바탕화면 프로그램을 실행하면 `바탕화면/logs`에 저장됩니다.

다시 사용할 때는 기존 프로그램을 종료하고 **v5.4.0**을 실행하세요. `조회(초)=3`, `출력 완료 대기(초)=60`으로 시작하면 됩니다. PC 주소·방화벽·장비 설정은 이번 수정에서 변경하지 않았습니다.

검증: 통신 시험 23개와 GUI 통합 시험 5개. 로컬 모의 장비에서 3.4초 지연 응답을 받는 동안 연결 유지, 명령 단일 전송, 다음 행 순서, 최종 시간 초과, STBY 취소, 장비 오류 4103 구분을 확인했습니다. 실제 5560A는 꺼져 있어 이번 수정의 실제 출력 재시험은 하지 않았습니다. USB/GPIB 시간 제한 처리는 모의 드라이버로만 확인했습니다.

60초까지 완료 응답이 없거나 장비가 `4103, Output settling timed out` 같은 오류를 반환하면, 단순히 제한 시간을 계속 늘리지 말고 자동 저장 로그와 본체 오류를 함께 확인해야 합니다. 그때는 실제 출력 안정화 문제와 통신 문제를 구분할 근거가 남습니다.

이전 점검 기록: 2026-10-29 실제 5560A에서 통신 복구를 확인했습니다. 장비 재시작 후 최신 코드로 연결·반복 조회·정상 해제·재연결을 3회 연속 통과했습니다.

## 이전 v5.3.1의 실제 장비 확인 기록

장비: `FLUKE,5560A,7165657,v4.00.07+v4.26.0001`

접속 경로: 실제 유선 랜카드 `192.168.100.100` → 장비 `169.254.1.1:3490`

검증 결과: 3회 모두 *IDN? 반복 조회 성공, OPER?=0, STBY 처리 완료 확인, LOCAL 처리 완료 확인, TCP 종료 및 다음 연결 성공.

최종 GUI 검증: v5.3.1 창에서 CONNECTED와 STANDBY 표시를 확인했습니다. 이는 이전 점검 당시의 기록입니다. 이번 v5.3.2 수정 시에는 사용자가 장비를 종료했으므로 실제 연결을 시도하지 않았습니다.

점검 중 두 문제가 구분되었습니다. 첫째, 자동 경로 사용 시 `10051`이 발생했고 유선 원본 주소 지정으로 통신에 성공했습니다. 둘째, 이후 `10061` 접속 거부가 발생했습니다. 장비 MAC `00:80:40:2D:1F:9F`에서 온 TCP RST 응답을 기록했으며, 사용자가 본체를 재시작한 뒤 해당 상태가 해소됐습니다. 접속 거부를 유발한 내부 원인까지 확정하지는 않았습니다.

같은 서브넷을 시험하기 위해 유선 랜카드에 `169.254.1.100/16`을 일시 추가했으나 통신이 개선되지 않아 정확히 그 보조 주소만 제거했습니다. 최종 PC 유선 설정은 원래의 `192.168.100.100/24`이며 Wi-Fi, DHCP, 방화벽 설정은 변경하지 않았습니다. 패킷 기록도 종료하고 임시 필터를 제거했습니다.

## 실행

`fluke_5560a_controller.py`를 실행하세요. LAN 통신에는 Python과 Tkinter만 필요합니다. 이 PC에는 이미 설치되어 있습니다.

현재 장비에 사용할 값:

| 항목 | 설정 |
|---|---|
| 모드 | LAN |
| 실제 랜카드 | 17: 이더넷 [Up] — Realtek PCIe GbE |
| 5560A IP | 169.254.1.1 |
| 포트 | 3490 |
| EOL | CRLF |
| 조회(초) | 3초: 연결 및 일반 조회 |
| 출력 완료 대기(초) | 60초: 명령 처리·출력 안정화 완료 응답 |

`LAN 진단`은 장비 식별만 조회합니다. `연결`은 장비 식별과 원격 통신 준비를 확인하고 실제 출력 상태를 읽습니다. 연결만으로 출력이 활성화되지는 않습니다. 출력은 OPER 또는 각 탭의 출력 동작으로 제어합니다.

기존 v5.3.2 이하 창은 수정 전 코드를 계속 실행합니다. 기존 창을 종료하고 제목이 **v5.4.0**인 최신 창을 사용하세요. 다른 제어 프로그램이 장비에 접속 중이면 그 LAN 연결을 먼저 해제해야 합니다.

## 확인된 원인과 실제 결과

기존 코드는 화면에서 고른 랜카드를 일반 LAN 연결에 적용하지 않았습니다. 소켓이 Windows 자동 경로를 사용했고, 이 환경에서 아래 차이가 재현됐습니다.

| 접속 방법 | 결과 |
|---|---|
| Windows 자동 경로, 원본 IP 미지정 | WinError 10051: 연결할 수 없는 네트워크 |
| 실제 유선 랜카드의 192.168.100.100 지정 | TCP 연결 및 *IDN? 성공 |

PC의 실제 유선 IP는 `192.168.100.100/24`, 장비의 IP는 `169.254.1.1/16`입니다. 일반적인 직결 구성에서는 같은 서브넷 설정이 필요하지만, 이 PC에서는 유선 원본 IP를 지정해 통신에 성공했습니다. 임시 보조 주소 시험 후 PC 설정을 원래대로 복원했습니다. 이 결과가 다른 PC나 네트워크에서도 보장되는 것은 아닙니다.

장비 사진에서 Network Security 첫 범위 `0.0.0.0~255.255.255.255`가 활성화되어 있고 Computer/CRLF/3490도 설정되어 있습니다. 이번에 확인한 장애를 장비 허용 범위 차단으로 볼 근거는 없습니다.

실제 장비 응답:

```text
*IDN?              FLUKE,5560A,7165657,v4.00.07+v4.26.0001
IPADDR?            169.254.1.1
SUBNETMASK?        255.255.0.0
ENETPORT?          3490
COMM_MODE? TELNET  COMP
EOLSTR? TELNET     CRLF
OPER?              0
ERR?               0,"No Error"  (최종 확인)
```

반복 조회 및 개선판의 연결 절차를 실제 장비에서 확인했습니다. 통신 점검에서는 전압·전류 설정 또는 OPER 명령을 보내지 않았습니다.

## 주요 변경

- 실제 하드웨어와 연결 상태를 조회하여 활성 유선 랜카드를 먼저 선택합니다. 가상/VPN 어댑터를 이름만 보고 고르던 방식을 제거했습니다.
- 선택한 랜카드의 실제 IPv4를 소켓 원본 주소에 적용합니다. 마스크를 무조건 /24로 가정하지 않습니다.
- TCP 연결만으로 성공 처리하지 않고 `FLUKE,5560A,...` 식별 응답을 검증합니다.
- TCP 분할 수신, CR/LF/CRLF, 명령 에코, 프롬프트, Telnet 협상을 처리합니다.
- 시간 초과로 통신 순서가 불확실해지면 연결을 닫아 늦게 온 응답을 다음 조회 결과로 오인하지 않게 했습니다.
- LAN 해제 시 종료 신호를 보내고 남은 데이터를 짧게 수신한 뒤 소켓을 정리합니다. 이는 접속 종료 처리 개선이며, 위 접속 거부의 원인이 규명됐다는 뜻은 아닙니다.
- 현재 Computer 모드인지 먼저 조회하고, Terminal 모드일 때만 설정을 변경합니다. 이미 맞는 통신 설정을 매번 다시 쓰지 않습니다.
- 원인별 오류와 선택한 PC IP를 보여주는 진단 및 진단 저장 기능을 추가했습니다.
- 연결·진단·랜카드 조회를 별도 작업으로 실행하여 화면 멈춤을 줄였습니다.
- 여러 대역의 PC IP를 강제로 설정하거나 DHCP를 원상복구로 오인하던 기능, 광범위 자동 포트 스캔을 제거했습니다.
- USB/GPIB의 VISA 오류 및 장비 검색 오류를 구분하고 실패한 핸들을 정리합니다. GPIB 모드는 지정 주소를 사용합니다. 이더넷용 REMOTE/LOCAL 문자열을 USB/GPIB에 보내지 않습니다.
- 명령 처리 완료와 장비 오류 응답을 확인합니다. 연결 끊김 시 화면의 출력 상태를 미확인으로 표시합니다.

## USB / GPIB

PyVISA와 NI-VISA 또는 해당 어댑터의 VISA 드라이버가 필요합니다. 현재 검사한 Python 환경에는 PyVISA 1.16.1과 VISA 라이브러리가 있지만, 검사 시 검색된 VISA 장비는 없었습니다.

USB는 후면 USB Device(B형) 포트를 사용하고 USBTMC를 활성화하세요. GPIB는 본체 주소와 프로그램 주소를 맞추세요. `VISA 리소스`에 NI MAX 등에서 확인한 전체 리소스를 입력하면 해당 리소스를 사용합니다. GPIB 보드가 0번이 아니면 이 입력란으로 지정할 수 있습니다.

USB/GPIB는 모의 드라이버로 로직을 검증했으며 실제 케이블/장비 연결 시험은 하지 않았습니다.

## 검증과 남은 사항

- 통신 회귀 테스트 17개 통과: 분할 응답, EOL, Telnet 협상, 잘못된 장비 거부, 무응답/EOF, 동시 조회, 핸들 정리, GPIB 주소 선택, 정상 해제/재연결, 필요한 경우에만 모드 변경 등.
- GUI 실행, 실제 유선 랜카드 기본 선택, 비동기 연결, 기존 표 초기화, 시뮬레이션 OPER/STBY 및 연결 해제를 확인했습니다.
- 실제 전압·전류·전력 출력 정확도 및 모든 출력 조합은 이번 LAN 개선 범위에서 검증하지 않았습니다.
- 점검 중 장비 오류 큐에서 `8012,"Zero adjustment is required every 14 days"`를 확인했습니다. 영점 조정 필요 여부는 장비 절차에 따라 확인해야 하며, 영점/교정 동작은 실행하지 않았습니다.
- 점검 중 잘못된 조회명 `NETMASK?`로 생긴 `-102,"Syntax error"`는 확인 후 올바른 `SUBNETMASK?`로 조회했습니다. 최종 오류 큐 조회는 `0,"No Error"`였습니다. 오류를 읽었다고 영점 조정 알림의 원인이 해소된 것은 아닙니다.
