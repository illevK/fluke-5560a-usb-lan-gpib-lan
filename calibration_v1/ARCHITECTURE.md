# 교정자동화 v1 설계 및 확장

## 의존 관계

화면 → 연결 서비스 / 실행 엔진 → 장비 드라이버 → 통신 계층으로 흐릅니다.
측정 문서와 실행 계획은 화면이나 실제 연결 없이 생성·검증할 수 있습니다.
Qt는 `ui`와 진입점에서만 사용합니다. 계측기 코드는 위젯을 알지 못합니다.

기존 v6.10.38의 통신·범위·SI 단위·클립보드 규칙을 독립 모듈로 옮겼습니다.
통신 드라이버를 처음부터 임의 명령으로 다시 작성하지 않았습니다. 기준 소스 해시는
`baseline.json`에 기록되어 있습니다. 새 버전은 `.pyfrag` 생성기나 기존 프로그램을
실행·import하지 않습니다.

## 실행 계약

1. 선택 행 이후 같은 논리 채널의 대상 그룹을 불변 실행 계획으로 만듭니다.
2. 행 식별자와 실행 식별자를 부여해 늦게 도착한 값이 다른 행이나 다음 실행에 기록되지 않게 합니다.
3. STBY 확인 → DUT 기능·범위·입력 설정 확인 → 기준기 조건 설정 → OPER 확인 → 유지시간 → 새 값 조회 순서입니다.
4. DUT 식별·채널·측정 항목·정류 방식·유한한 숫자 여부 및 기준기 출력 상태를 확인한 값만 기록합니다.
5. 종료·오류·단자 경계에서는 STBY를 확인합니다. 자동으로 다른 채널이나 다른 단자로 넘어가지 않습니다.
6. 진행 보류는 현재 출력 유지입니다. 정지는 취소 이벤트를 설정하고 별도 기준기 작업으로 STBY를 요청합니다.
   기준기 명령 잠금과 OPER 차단 래치 때문에 기존 출력 명령을 취소한 뒤 다시 출력하지 않습니다.
7. 통신 실패와 장비 보호 오류를 구분합니다. 복구는 장비 식별을 다시 확인하며 자동 출력 재시작을 하지 않습니다.
8. 기준기만 연결하면 기본은 유지시간에 따른 자동 진행입니다. 편집 중인 측정값과 기준기의 출력 행은
   독립적입니다. 입력 대기 방식을 선택하면 Enter로 받은 값의 실행·행 식별자와 기준기 출력을 확인한
   뒤 기록합니다. DUT 자동 기록 중 연결이 끊기면 해당 행을 중단합니다.

일반 I/O는 하나의 작업 큐에서 처리하고, 긴 DUT 응답으로 STBY가 지연되는 경우를 위해
정지 작업만 기준기 잠금을 통해 별도로 처리합니다. USB/VISA 드라이버 호출 자체가
OS 안에서 멈추면 프로그램이 실제 출력 상태를 보장할 수 없으므로 미확인 상태를 표시합니다.

## DUT 추가

`services/drivers.py`의 `DriverRegistry`에 다음을 등록합니다.

- 이름과 프로필 매칭 조건
- 연결 화면에 표시할 이름과 검색할 계열 또는 모델을 짝지은 목록(choices)
- `DUTSession`을 받아 드라이버를 만드는 팩토리
- 필요한 경우 정확한 제조사·모델 식별 함수와 LAN 식별 프로브

드라이버는 `initialize()`, `prepare(point, standby)`, `capture(point, resistance_null=False)`를 구현합니다.
`initialize`는 지원되는 기본 설정만 적용하고 응답으로 확인합니다.
`prepare`는 행의 기능과 입력 단자를 자동 선택하며, 지원하지 않는 항목은 기준기 출력 전에 거절합니다.
`capture`는 새 데이터를 확인하고 `DUTSample`의 identity/channel/values/raw_values를 채웁니다.
값의 기본 단위와 지표 이름은 `domain/planning.py`의 `QUANTITIES`를 따릅니다.
새 계열의 수동 현재 값 조회를 추가할 때는 해당 계열의 `DUTSession.read`도 구현합니다.

LAN 플러그인은 문서로 확인한 `SCPI_TCP` 또는 `VXI11`만 등록합니다.
AUTO는 장비 식별 전에는 출력·설정 명령을 보내지 않습니다.
직결 LAN은 사용자가 지정한 장비 IP/서브넷에 한해 기존 유선 주소/경로 정렬 코드를 사용합니다.
USB·RS232·GPIB도 장비의 실제 인터페이스, 드라이버와 원격 설정이 있어야 사용할 수 있습니다.

새 계열은 최소한 식별, 단위와 채널, DC/AC 전환, 읽기 지연/오류, 정지 중 응답 도착,
지원하지 않는 기능의 사전 차단을 모의 장비로 검사한 뒤 실물 검사를 진행합니다.
본문을 치환하는 패치 파일이나 UI 콜백에 장비 명령을 추가하는 방식을 사용하지 않습니다.

## 배포

`build.py`는 Python과 Windows 기본 경로만 사용해 DLL 의존성을 찾습니다.
이 PC의 개발 도구 PATH에 있던 Poppler용 `icuuc.dll`이 Qt의 Windows ICU 의존성을
가로채어 첫 EXE에서 로드 오류가 발생한 것을 확인했습니다. 원본 Python 실행은
정상이었으므로 소스 검사와 별도로 최종 EXE 자체를 실행해 확인합니다.
`verify_release.py`는 빈 초기 화면, 가상 DC→AC 측정, GUI 이미지 생성, 통신 모듈과
Windows 표시 플러그인 포함 여부 및 버전 정보를 검사합니다. 실제 장비를 연결하지 않습니다.

## 데이터와 화면

`Document`는 원본 입력과 원본 측정값을 보관합니다. 변환은 표시·복사 시 수행하므로
명목값 단위 변경으로 원본의 의미가 달라지지 않습니다. 행 순서를 바꿔도 UUID와 원래 순서를 보관합니다.
프로젝트 JSON은 임시 파일을 쓰고 원자적으로 교체합니다.

표는 Qt 모델/뷰를 사용해 행마다 편집 위젯을 만들지 않습니다. 통신 로그의 화면 표시도
800줄로 제한하며 파일에는 전체 기록을 남깁니다. 진행률과 로그 패널에만 짧은 전환 효과를 사용합니다.
실제 OPER/STBY 상태 표시는 효과를 기다리지 않습니다. 설정에서 효과를 끌 수 있습니다.

`tests/protocols`는 이전 구현의 비GUI 회귀 검사를 새 모듈에 연결합니다.
`tests/api_compat.py`는 테스트에만 쓰는 이름 매핑이며 배포 파일에서 사용하지 않습니다.
`tests/test_workflow.py`, `test_device_workflow.py`, `test_connections.py`, `test_ui.py`는
새 실행 계약, 장비 간 순서, 드라이버 확장, 화면과 대량 표 동작을 검사합니다.
